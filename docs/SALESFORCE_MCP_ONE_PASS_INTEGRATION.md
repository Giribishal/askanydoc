# AskAnyDoc ↔ Salesforce Hosted MCP: one-pass web integration

**Verified configuration:** 3 October 2026, Australia/Brisbane. This is the ordered recipe for the Developer Edition, one-user, read-only Case slice tested in the deployed AskAnyDoc UI. The [append-only integration ledger](SALESFORCE_MCP_INTEGRATION_PLAN.md) records what actually happened, including failed attempts and reversals. The [SF1 fixture record](SALESFORCE_SF1_FIXTURE_AND_EVIDENCE.md) records the fictional CRM data. This guide is the desired sequence for a **fresh** build; it is not an instruction to delete and recreate the current working connection.

Follow each stage in order and record a dated read-back before advancing. Do not paste a Consumer Secret, OAuth code, access/refresh token, password, or verification code into chat, Git, Terraform state, screenshots, or command arguments. A current official Salesforce UI or API response overrides a stale label in this dated recipe; stop and update the recipe when a required setting or live schema differs. No procedure can promise zero errors after a vendor or environment change.

## What the working connection does

1. The employee signs into AskAnyDoc with Microsoft Entra. The existing protected API verifies that token and derives a stable tenant/user-specific grant owner; the Entra email does **not** need to match the Salesforce username.
2. The employee separately authorizes `AskAnyDoc Salesforce Web Dev` in Salesforce through Authorization Code + PKCE. Salesforce's permissions govern the Cases that employee can read. The ECA authorizes the client; it does not grant all Salesforce data.
3. A dedicated Salesforce Lambda stores the user's OAuth grant in AWS Secrets Manager under `askanydoc/salesforce-grants-dev/`; only that Lambda can read it. It calls Salesforce's hosted **SObject Reads** MCP server. The current application route accepts **one explicit Case record ID**, performs a bounded `soqlQuery`, validates the returned record, and cites the Salesforce Case URL. Other Salesforce objects and natural-language searching are not in this proven UI slice.
4. `Connections → Salesforce` shows Connected/Not connected, org, read-only Case scope, and user-controlled **Disconnect** and **Change account** actions. Disconnect posts the current user's refresh token to Salesforce's revocation endpoint and replaces the current saved grant with a token-free tombstone. Change account does that first, then starts a new OAuth request with `prompt=login`. The UI asks the user to confirm before either action. The controls and unit tests passed; **live revocation of the current user grant has not been exercised**, to preserve the working connection.

## Stage 1 — Enable only Salesforce's read server

1. In the intended Salesforce org, open **Setup → Integrations → API Catalog → MCP Servers → SObject Reads**. Confirm the server ID is `platform.sobject-reads`, the production endpoint is `https://api.salesforce.com/platform/mcp/v1/platform/sobject-reads`, and it exposes exactly the six read tools `getRelatedRecords`, `listRecentSobjectRecords`, `soqlQuery`, `find`, `getUserInfo`, `getObjectSchema`.
2. Activate **SObject Reads** if it is inactive; read back **Active**. Leave other MCP servers unchanged. The current Developer Edition showed a possible-billing warning but no purchase/terms prompt during this tested activation. Stop if a new payment, upgrade, licence or binding-terms prompt appears.

**Gate:** Active server and six-tool catalogue are visible. Activation proves availability, not a successful authenticated read.

## Stage 2 — Restrict the Salesforce user before the web client can be used

1. In Setup → Users → Permission Sets, create `AskAnyDoc Salesforce MCP Read Dev` with API name `AskAnyDoc_Salesforce_MCP_Read_Dev`, License `--None--`, Session Activation Required off. This set controls **who may authorize the ECA**; it adds no object or system permissions.
2. Assign only the intended development Salesforce user. Record the actual assignment expiry and time zone. The first run used Bishal's user `005bm00000YjRenAAF`, a 30-day assignment expiring **2 November 2026** in `Australia/Sydney`; choose a new future expiry on rebuild. A user without this set should not be able to authorize the ECA.

**Gate:** The assignment read-back shows exactly the intended user and future expiry. Salesforce object/field/record sharing remains whatever that user already has.

## Stage 3 — Create the final **web** External Client App once

1. Setup → Apps → External Client App Manager → New External Client App. Create `AskAnyDoc Salesforce Web Dev` / API name `AskAnyDoc_Salesforce_Web_Dev`, Enabled, distribution `Local`. Enter the intended admin contact email in Salesforce; do not copy it into public docs. Use a description stating this is the read-only, user-authorized AskAnyDoc development web client.
2. Enable OAuth. Register the **final HTTPS callback** `https://d2vyg7cbej561m.cloudfront.net/` for this deployment. Select only `mcp_api` and `refresh_token/offline_access`. Enable Authorization Code and Credentials Flow, require PKCE, require the server-held Consumer Secret for web authorization and refresh, issue named-user JWT access tokens, and keep rotating refresh tokens with the observed 30-day idle validity. Leave client credentials, device, JWT bearer, token exchange, user-credentials-in-POST, introspection and ID-token configuration off. Keep IP restrictions and all other security defaults at the saved values unless a separately approved, documented change is necessary.
3. **Before first authorization**, open Policies → OAuth Policies → Edit and set `Permitted Users` to **Admin approved users are pre-authorized**. Select only `AskAnyDoc Salesforce MCP Read Dev`; select no profiles. Save, then read back both the policy and the Settings page, including callback, scopes and all relevant toggles. The first run's default was “All users can self-authorize”; leaving that default is not this approved architecture.
4. The older `AskAnyDoc Salesforce Read Dev` **local-probe** ECA with a localhost callback was a diagnostic SF2/SF3 client. It is not the web ECA and is not required for a clean web connection. Do not reuse its Consumer Key or localhost callback for this stage.

**Gate:** The saved web ECA is Enabled/Local, has the exact HTTPS callback and two scopes, and preauthorizes only the assigned permission set. No user grant or token exists yet.

## Stage 4 — Deploy only the dedicated AskAnyDoc Salesforce path

1. Review `infra/salesforce_web.tf`, `app/salesforce/web_handler.py`, `app/salesforce/read_adapter.py`, `infra/build_salesforce_web.ps1`, `frontend/src/App.jsx`, `Sidebar.jsx`, `authConfig.js`, and `App.css`. The working design uses a separate Python 3.13 Lambda `askanydoc-salesforce-web-dev` (512 MiB, 29-second timeout), its dedicated IAM role, 30-day CloudWatch log retention, a TTL DynamoDB OAuth-state table, a web ECA client secret, per-user grant secrets, and the **existing** JWT-protected API. The SObject Reads Python MCP SDK is pinned at `mcp==1.30.0` in the tested package; recheck its security advisories before rebuilding.
2. The protected API has `POST /salesforce/connect`, `POST /salesforce/complete`, `GET /salesforce/status`, `POST /salesforce/ask`, and `POST /salesforce/disconnect`. Each route uses the existing Entra JWT authorizer and `access_as_user` scope. No anonymous route is allowed. CORS remains restricted to the CloudFront origin.
3. The dedicated IAM policy allows the OAuth-state table `PutItem`/`DeleteItem`, `GetSecretValue` for `askanydoc/salesforce-web-client-dev`, and `CreateSecret`, `GetSecretValue`, `PutSecretValue`, **`TagResource`** only for `askanydoc/salesforce-grants-dev/*`. `TagResource` is required by the tagged grant creation; omitting it produced a real `AccessDeniedException`. It also allows the specific Bedrock model used by the Salesforce answer. Do not give this Lambda a wildcard AWS/SharePoint data role.
4. Build the Salesforce package with `infra/build_salesforce_web.ps1`. The first tested Windows package needed separate Linux dependency installation followed by `mcp==1.30.0 --no-deps` to avoid Windows-only `pywin32`. Do not set reserved concurrency to 1 in this AWS account; AWS rejected it because ten unreserved executions must remain. A later multi-user release needs a per-user refresh lock and additional permission-isolation testing.
5. Build and lint the frontend. Review a Terraform plan with **both** `-var=salesforce_web_enabled=true` and `-var=salesforce_org_origin=<the verified exact HTTPS My Domain origin>`. The flag's default is false; omitting it previously generated a **destructive** plan for the working connector and must never be applied. Scope the plan to the Salesforce resources and frontend when unrelated pre-existing AWS/SharePoint drift exists; record every targeted resource and review all create/update/destroy actions before apply. Do not apply a stale saved plan.
6. Apply the reviewed plan; read back the five API route keys/authorization, Lambda package/runtime/timeout, IAM resource prefixes, secret metadata (not values), state-table TTL, frontend S3 objects and CloudFront origin. Invalidate `/` and `/index.html` on distribution `E302MAX0PA60NZ` for this deployment. `POST /salesforce/disconnect` without a JWT returned **401** in the 3 October 2026 test.

**Gate:** Only the reviewed Salesforce-specific resources/frontend changed. Existing `/jobs`, `/chat`, AWS retrieval, and SharePoint deployment are still present. A browser sign-in and Salesforce OAuth are still needed to prove application behavior.

## Stage 5 — Enter the web ECA credentials without exposing them

1. The Salesforce user opens the saved web ECA's Settings → OAuth Settings → **Consumer Key and Secret** and completes any emailed identity step-up personally. Do not inspect or capture the secret page.
2. The user runs `infra/set_salesforce_web_client.py` in their own terminal. Its hidden prompts store each exact value **once** in AWS Secrets Manager `askanydoc/salesforce-web-client-dev`; the values must never be supplied as command-line arguments or in Terraform variables. Verify only that an `AWSCURRENT` version exists. The first run accidentally pasted both values twice; it required the no-echo exact-half repair helper. That repair is **not** part of the normal recipe. Verify length/shape without printing values before OAuth.

**Gate:** Secret metadata confirms a current version; no Consumer Key/Secret appears in logs, shell history, docs, Git or Terraform state.

## Stage 6 — Authorize one user, then prove the record and answer

1. Sign into the deployed AskAnyDoc site with the intended Entra user. Open **Connections → Salesforce → Connect Salesforce**, then use the explicit **Continue to Salesforce** link. The link should point to `https://login.salesforce.com/services/oauth2/authorize` and carry Authorization Code + PKCE SHA-256, `mcp_api refresh_token`, a 10-minute owner-bound state, and the exact registered callback. Do not enter credentials in AskAnyDoc itself.
2. Authorize as the intended, preauthorized Salesforce user. Salesforce can use a different email from Entra. It returns to the CloudFront root; the frontend removes `code`/`state` from browser history and calls the Entra-protected `/complete` route. The backend requires matching state/owner, exchanges the code using the server-held secret and verifier, requires the exact expected `instance_url` and a refresh token, and saves the grant only under that Entra tenant/user owner. The UI must show **Connected**.
3. Ask: `What is the status and priority of Salesforce Case 500bm00003BZO62AAH?` The 3 October 2026 deployed result was `New`, `High`, Case `00001027`, the VPN subject, and a clickable citation to the exact Case. The live `soqlQuery` MCP input schema required **`q`**, even though Salesforce's prose reference said `query`; the adapter sends `q`, with a Case `Id` predicate and `LIMIT 1`. The MCP HTTP timeout is 20 seconds; the earlier 12-second setting timed out.
4. Ask for absent Case `500000000000000AAA`: it must not fabricate Case facts or a citation. Run an existing AWS document question, a known SharePoint document question with page citations, and a mixed AWS/SharePoint question. An alternative SharePoint wording previously returned an uncited answer; keep that attribution issue open rather than claiming exhaustive reliability.
5. Open the Salesforce settings and check Connected, org, read-only Case scope, Change account and Disconnect. Confirm the account-switch confirmation can be opened and cancelled with no change. A live **revoke-and-reconnect** test should be done with an explicitly chosen test grant when the user is ready; do not revoke a working user's grant merely to prove the button exists. Change account uses Salesforce `prompt=login`; Salesforce still decides which credentials can authorize.

**Gate:** A real UI Case answer and Case citation match the Salesforce record, negative Case behavior is honest, and AWS/SharePoint smoke checks pass. OAuth/tool listing alone is insufficient. Current proof covers **one** Entra user and one Salesforce identity, not permission isolation between two employees.

## Scope after the first Case proof

The Case-ID route is a first acceptance gate, not the intended end state of the Salesforce connection. Bishal's 3 October 2026 requirement is to ask natural-language questions such as “Are there Salesforce cases about VPN?”, “What is the phone number of a contact at this company?”, “Which company does this contact belong to?”, and “What notes, tasks or events relate to this account?” without copying a Case ID. Keep the same user-bound OAuth grant and SObject Reads server. Salesforce's current [SObject Reads catalogue](https://developer.salesforce.com/docs/platform/hosted-mcp-servers/guide/sobject-reads.html) exposes schema discovery, cross-object `find`, bounded SOQL and related-record traversal, subject to each Salesforce user's object, field and sharing permissions. AskAnyDoc must implement a bounded planner/executor and citation shaping for the record types it supports; the server alone does not make the current UI answer these questions.

Next build gate: inspect the **live** schema and tool input/output for Account, Contact, Case, Opportunity, Lead, Task, Event, and the actual Note object/link visible in this org. Do not assume Notes or Chatter behave like ordinary queryable CRM fields. Add a documented, allowlisted set of read operations with query/result limits, output validation, per-record citations, no user-supplied raw SOQL, and honest no-access/no-match answers. Test at least one populated and one absent/unauthorized example per object family through the deployed UI. Broader Salesforce CMS/files, Chatter, Setup, reports and analytics require their own capability and permission checks; “read everything” is not a verified property of SObject Reads. The web ECA's restricted-user permission set also must be assigned to any additional Salesforce identity before Change account can authorize it.

3. Open release gates remain: live disconnect/reconnect with a chosen test user, refresh-token rotation and revocation behavior, concurrent per-user refresh locking, two-user Salesforce permission isolation, a broader object/field/record-level negative test, and the prompt-sensitive SharePoint attribution case. Do not call the integration production-ready until those pass.
