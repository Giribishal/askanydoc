## What the working connection does

1. The employee signs into AskAnyDoc with Microsoft Entra. The existing protected API verifies that token and derives a stable tenant/user-specific grant owner; the Entra email does **not** need to match the Salesforce username.
2. The employee separately authorizes `AskAnyDoc Salesforce Web Dev` in Salesforce through Authorization Code + PKCE. Salesforce's permissions govern the records and fields that employee can read. The ECA authorizes the client; it does not grant all Salesforce data.
3. A dedicated Salesforce Lambda stores the user's OAuth grant in AWS Secrets Manager under `askanydoc/salesforce-grants-dev/`; only that Lambda can read it. It calls Salesforce's hosted **SObject Reads** MCP server. The explicit Case-ID path remains available. Questions explicitly naming **Salesforce** also use a typed, bounded planner in `app/salesforce/crm_reader.py`: Accounts, Contacts, Cases, Opportunities, Leads, Tasks, Events and classic Notes. The application compiles allowlisted SOQL; a model or user cannot submit arbitrary queries. At most three object reads plus one Account resolution return up to ten recent records per type, with application-built record citations. Contact.Account.Name supports contact-to-company lookup. No model-generated query or record URL is trusted.
4. `Connections → Salesforce` shows Connected/Not connected, org, read-only CRM scope, and user-controlled **Disconnect** and **Change account** actions. Disconnect posts the current user's refresh token to Salesforce's revocation endpoint and replaces the current saved grant with a token-free tombstone. Change account does that first, then starts a new OAuth request with `prompt=login`. The UI asks the user to confirm before either action. The controls and unit tests passed; **live revocation of the current user grant has not been exercised**, to preserve the working connection.

## Scope after the first Case proof

The Case-ID route is a first acceptance gate, not the intended end state of the Salesforce connection. Bishal's 3 October 2026 requirement is to ask natural-language questions such as “Are there Salesforce cases about VPN?”, “What is the phone number of a contact at this company?”, “Which company does this contact belong to?”, and “What notes, tasks or events relate to this account?” without copying a Case ID. Keep the same user-bound OAuth grant and SObject Reads server. Salesforce's current [SObject Reads catalogue](https://developer.salesforce.com/docs/platform/hosted-mcp-servers/guide/sobject-reads.html) exposes schema discovery, cross-object `find`, bounded SOQL and related-record traversal, subject to each Salesforce user's object, field and sharing permissions. AskAnyDoc now implements the bounded planner/executor and citation shaping in the dedicated Salesforce path; the hosted server performs the authorized reads, while AskAnyDoc plans and generates the grounded answer.

**4 October 2026 gate result:** The live six-tool catalogue and schemas for Account, Contact, Case, Opportunity, Lead, Task, Event and classic Note were checked. Both `soqlQuery` and `find` require `q`; `getObjectSchema` takes `objects`, contradicting the current prose parameter names. Targeted fictional reads passed for all eight object types. The deployed UI passed VPN Case search, Rivergum company/contact phones, Bluehaven classic Note/Event/Opportunity, Amberpoint Task/Note, Lead, no-match and the original Case-ID route. Salesforce UI confirms the inspected Bluehaven Note Body is blank; unavailable text must not be invented. Enhanced `ContentNote` was rejected by this server during discovery and remains unsupported. Two early multi-record UI attempts returned an MCP protocol error; later SDK/UI checks passed, and sanitized code/category diagnostics were added. Intermittent protocol failure root cause remains unconfirmed. Broader reliability and permission-negative gates remain open.

For any later scope expansion, inspect the **live** schema and tool input/output for the actual object/link in this org. Do not assume Notes or Chatter behave like ordinary queryable CRM fields. Add a documented, allowlisted set of read operations with query/result limits, output validation, per-record citations, no user-supplied raw SOQL, and honest no-access/no-match answers. Test at least one populated and one absent/unauthorized example per object family through the deployed UI. Broader Salesforce CMS/files, Chatter, Setup, reports and analytics require their own capability and permission checks; “read everything” is not a verified property of SObject Reads. The web ECA's restricted-user permission set also must be assigned to any additional Salesforce identity before Change account can authorize it.
