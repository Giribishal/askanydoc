# Salesforce read-only MCP: teardown and one-pass rebuild

**Current web-app rebuild path:** use [the ordered one-pass web guide](SALESFORCE_MCP_ONE_PASS_INTEGRATION.md). This older runbook retains the SF2/SF3 local-probe learning sequence and historical checkpoints; its early claims that the web connector is not deployed were superseded by the dated integration ledger. Do not follow its local ECA/localhost callback as the web-app setup.

Checkpoint: 3 October 2026, Australia/Brisbane. This is a reproducible **Developer Edition learning setup**, not a production rollout. The exhaustive action history and exact deviations are in [the integration ledger](SALESFORCE_MCP_INTEGRATION_PLAN.md); the fictional CRM inventory is in [SF1 evidence](SALESFORCE_SF1_FIXTURE_AND_EVIDENCE.md). Do not confuse the proven Salesforce-only read with a deployed AskAnyDoc connection.

## Intended result and acceptance

An authorized Salesforce user can let a local AskAnyDoc adapter read a specific Case through Salesforce's hosted **SObject Reads** MCP server. The query is built by our code, includes an indexed Case `Id` predicate and `LIMIT 1`, and yields a Case record URL for citation. The opt-in local AskAnyDoc answer path uses those verified facts and returns a grounded Case citation. A missing ID returns no evidence. AWS document retrieval and SharePoint stay untouched. Successful OAuth and tool discovery alone do not satisfy the Case-read and answer checks.

The architecture has three separable parts: Salesforce owns data and user permissions; the hosted MCP server exposes read tools; AskAnyDoc owns source selection, bounded queries, evidence validation, citations and answer generation. Postman or Inspector is a **temporary diagnostic client**, never a component in the eventual request path. The current local probe uses the official Python MCP SDK and the existing AskAnyDoc answer function, with no production Salesforce OAuth infrastructure. A deployed, multi-user AskAnyDoc connector additionally needs a reviewed Salesforce sign-in callback, per-user grant storage, token refresh/revocation, and handler/worker wiring. Those are **not configured yet**.
