## User outcome and scope

AskAnyDoc (called “Askinator” conversationally) should answer a question such as “What is the status and priority of Rivergum's VPN case?” using live, permission-allowed Salesforce records, with a verifiable Account/Case citation. The Salesforce fixture is documented in [SF1 evidence](SALESFORCE_SF1_FIXTURE_AND_EVIDENCE.md). The first integration must only read data. The existing AWS document retrieval and SharePoint paths must keep working as before. This is a learning/dev slice, not a claim of secure multi-user release.

Two separate proofs are required:

1. **SF2, Salesforce-only proof:** connect the official MCP Inspector through OAuth to Salesforce's hosted `platform/sobject-reads` MCP server. Confirm the tool catalogue and one known Case against the Salesforce UI. This proves Salesforce access, **not** AskAnyDoc integration. 2. **SF3, AskAnyDoc local/dev proof:** add a thin, bounded Salesforce client adapter with one isolated Salesforce test identity. AskAnyDoc itself routes a customer-case question, requests allowed records through MCP, builds evidence and a citation, and answers honestly. This requires a separate code/security review and approval before shared worker or AWS-path changes. No production or multi-user release in SF3.

## Capability, authorization and processing boundary

Only `platform/sobject-reads` is proposed. Its published tools are `getObjectSchema`, `soqlQuery`, `find`, `getUserInfo`, `listRecentSobjectRecords`, and `getRelatedRecords`. It can retrieve schema and allowed records; it cannot create, edit, or delete records. Do **not** activate `sobject-all`, mutations, deletes, Headless 360, or other broad servers for this proof. Salesforce authorization still depends on the authenticated user's object/field/record/sharing rights and the ECA's OAuth policy. Having the read tool does not imply a user may see every record. Retrieval is not answer generation or semantic document RAG: AskAnyDoc must bound the query, select evidence, and generate a supported answer itself. [Tool reference](https://developer.salesforce.com/docs/platform/hosted-mcp-servers/guide/sobject-reads.html).

## SF3 AskAnyDoc design; protected-path wiring requires a separate exact-impact approval

The code currently defines AWS/SharePoint tools in `app/api/organisation_tools.py` and routes/normalises evidence in `app/api/assistant_orchestrator.py`. The answer Lambda and asynchronous worker package those files in `infra/answer_lambda.tf` and `infra/answer_jobs.tf`. Existing Entra/SharePoint sign-in is **not** Salesforce authorization. An Inspector token is **not** an AskAnyDoc connection. Before any protected shared-code SF3 edit, decide and document:

**Post-SF2 code inspection, 2026-10-03:** `app/api/answer_lambda_handler.py` obtains an Entra `user_id`, `tenant_id`, and bearer token; `app/api/answer_job_api_handler.py` places that context into an SQS answer job; `app/api/answer_job_worker.py` validates it. `app/sharepoint/source_router.py`, `app/api/organisation_tools.py`, and `app/api/assistant_orchestrator.py` currently know only AWS/SharePoint. They have no Salesforce OAuth grant or account/case evidence path. Therefore the verified Inspector token cannot be inserted into AskAnyDoc safely by a single MCP URL setting. The actual application boundary requires a separately authorized Salesforce identity flow and token lifecycle, a bounded Salesforce MCP adapter, and an opt-in route/evidence integration. The Inspector/local-probe callback must not be reused as the deployed AskAnyDoc callback. Preserve the current Entra/AWS/SharePoint request handling; the isolated `app/salesforce/` development files have been added, but no existing application file or infrastructure has changed for SF3.

**Smallest reviewable SF3 implementation:** first add an isolated local/development Salesforce client and OAuth callback using the official MCP SDK with a pinned, security-reviewed version; use only the saved `SObject Reads` endpoint and user-delegated OAuth PKCE, with tokens kept out of Git, logs, browser local storage, model prompts and SQS payloads. Expose one application-owned operation: a bounded lookup of a Case by ID or Account plus narrow fields, returning normalized record evidence and URL. Show a correct Rivergum answer and an honest missing-record result in local development. Only after that proof, present a precise additive shared-router/handler/worker diff and tests for Bishal's approval under the protected AWS-path rule; keep the Salesforce feature off by default and do not change AWS/SharePoint retrieval behavior or deployed resources as part of the local slice. The current [MCP Python SDK OAuth advisory](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99) must be checked against the pinned version before using it; a new dependency is not justified until it is part of the local slice.

1. **Identity and OAuth:** one isolated Salesforce test user in local/dev only; exact AskAnyDoc callback, client type, PKCE/state/CSRF handling, token storage, expiry/refresh/revocation, Salesforce org/user binding, and logout. Never put tokens in the browser's local storage, Git, Lambda environment variables, logs, or model prompt. Decide whether a separate ECA is required for the different callback and access policy; do not reuse Postman registration by assumption.
2. **Adapter:** new thin Salesforce MCP client module with the discovered protocol/transport, explicit endpoint, request timeout, bounded retries, input/output limits, and safe errors. First get identity/schema with an isolated diagnostic, then application-build SOQL. The model may request a high-level customer/case lookup but must never supply arbitrary SOQL/SOSL or select unrestricted objects/fields. Allowlist `Account`, `Case`, and only additional proven fields/relationships needed by the acceptance question; row cap and `WHERE`/`LIMIT` are mandatory. Expand to Contacts/Opportunities/Notes/Tasks only on a separately evidenced use case.
3. **Evidence and routing:** add a Salesforce source/tool only when auth and feature flag are present; convert record ID, object, field, Account link, modified time if available, and Salesforce record URL into citation-ready evidence. Keep restricted audit metadata out of user-visible answers; preserve source-specific no-result and permission-denied behavior. Do not make AWS or SharePoint calls for an explicit Salesforce-only question. Keep AWS and SharePoint tests green.
4. **Execution boundary:** prefer a local/dev harness first. Any modification to shared orchestration, worker packaging, Terraform, deployment environment, or existing AWS-path behavior requires a documented diff and the separate protected-path approval required by workspace `AGENTS.md` immediately before the change. No deploy until reviewed.
5. **Tests:** unit tests for allowlist, bounded query, malicious/oversized input, timeout, bad token, wrong org, no records, denied field, evidence provenance and citation; then one live AskAnyDoc local/dev answer grounded in the known Case, compared with UI; inspect logs for secret leakage. Two-user/field-denial isolation is SF5, not claimed here.

Acceptance for SF3 is a Salesforce-specific AskAnyDoc answer with correct Case status and a record citation, plus an honest missing-data answer and no regression to the existing AWS/SharePoint routes. Mere MCP tool availability or a successful Postman call is insufficient.
